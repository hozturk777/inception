# Inception

## Description

Inception is a system administration project: a small web infrastructure built with
Docker Compose inside a virtual machine. Every service runs in its own container, built
from a Dockerfile written for this project on top of `debian:bookworm` (the penultimate
stable Debian release). No ready-made service images are pulled.

The stack:

| Service     | Role                                                   | Port (internal) |
|-------------|--------------------------------------------------------|-----------------|
| `nginx`     | Only entrypoint, HTTPS with TLSv1.2/TLSv1.3 only        | 443 (published) |
| `wordpress` | WordPress + php-fpm (no web server)                     | 9000            |
| `mariadb`   | Database for WordPress                                  | 3306            |

```
Browser ──443/TLS──► nginx ──FastCGI 9000──► wordpress ──3306──► mariadb
                       │                        │                   │
                       └──── wordpress_data ────┘             mariadb_data
                          (/home/huozturk/data/wordpress)  (/home/huozturk/data/mariadb)
```

## Instructions

Prerequisites: a Linux VM with Docker Engine, the Docker Compose plugin, `make`,
`openssl` and `sudo`.

```sh
# 1. Point the domain to the local machine
echo "127.0.0.1 huozturk.42.fr" | sudo tee -a /etc/hosts

# 2. Build and start everything (secrets are generated on first run)
make

# 3. Open the site (accept the self-signed certificate warning)
#    https://huozturk.42.fr          -> website
#    https://huozturk.42.fr/wp-admin -> administration panel
```

Other targets: `make down`, `make stop`, `make start`, `make ps`, `make logs`,
`make clean` (containers, images, volumes), `make fclean` (also deletes host data),
`make re`.

See [USER_DOC.md](USER_DOC.md) and [DEV_DOC.md](DEV_DOC.md) for details.

## Project description

### Use of Docker and sources

```
.
├── Makefile                  # builds and runs everything through docker compose
├── secrets/                  # passwords (git-ignored, generated by make)
└── srcs/
    ├── .env                  # non-secret configuration (domain, user names, ...)
    ├── docker-compose.yml    # services, network, volumes, secrets
    └── requirements/
        ├── mariadb/   Dockerfile, conf/50-server.cnf, tools/entrypoint.sh
        ├── wordpress/ Dockerfile, conf/www.conf, tools/entrypoint.sh
        └── nginx/     Dockerfile, conf/inception.conf.template, tools/entrypoint.sh
```

### Main design choices

- **One process per container, as PID 1.** Each entrypoint script prepares the service
  (first-run setup) and then `exec`s the real daemon in the foreground
  (`mariadbd`, `php-fpm8.2 -F`, `nginx -g "daemon off;"`). No `tail -f`, `sleep`
  or infinite loops; the daemon receives signals directly and `docker stop` is clean.
- **Idempotent initialization.** Database and WordPress setup only run when the data is
  missing, so restarting containers keeps existing data.
- **Startup order.** `wordpress` waits until `mariadb` passes its healthcheck
  (`mysqladmin ping`), so the WordPress installer never hits an unready database.
- **TLS.** The self-signed certificate is created when the nginx container starts, so
  the private key is never baked into an image layer. `ssl_protocols TLSv1.2 TLSv1.3`.
- **Images** are tagged `:1.0` (named after their service) because the `latest` tag is
  prohibited.
- **Restart policy** `always`: a crashed container is restarted by Docker.

### Virtual Machines vs Docker

A virtual machine emulates hardware and runs a full guest kernel; it is strongly
isolated but heavy (GBs of disk, slow boot). A Docker container shares the host kernel
and isolates processes with namespaces and cgroups; it starts in milliseconds and is
light, but isolation is weaker. Here both are used: the VM is the host, containers run
the services.

### Secrets vs Environment Variables

Environment variables are visible in `docker inspect`, in `/proc/<pid>/environ` and
are inherited by child processes, so they suit non-sensitive configuration (domain,
user names). Docker secrets are mounted as files under `/run/secrets/` only in the
containers that declare them and do not appear in the container's environment. In this
project `.env` holds configuration only, and all passwords are secrets.

### Docker Network vs Host Network

With `network: host` a container shares the host's network stack: no isolation, every
port it opens is exposed on the host. A user-defined bridge network (`inception`) gives
containers a private network with built-in DNS (`mariadb`, `wordpress` resolve by
name); only the explicitly published port 443 is reachable from outside.

### Docker Volumes vs Bind Mounts

A bind mount maps an arbitrary host path into a container and depends on the host's
directory layout. A named volume is a Docker-managed object (`docker volume ls`) with a
lifecycle independent of containers. This project uses named volumes
(`mariadb_data`, `wordpress_data`) with the `local` driver configured so that their data
is stored in `/home/huozturk/data`, as required by the subject.
